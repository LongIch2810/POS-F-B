## Các bước thực hiện và đầu ra

### 1. Kiểm kê và đối chiếu

1. Đọc tài liệu liên quan, dùng graph tìm symbol/caller của PlatformController, Users controller, PlatformService, AccessGuard, AuthService và platformService UI; fallback đọc file khi graph thiếu hoặc cũ.
2. Lập bảng yêu cầu → spec → mã → test → artifact cho từng ô sprint; liệt kê sai lệch, không suy từ test pass ra đủ nghiệm thu.
3. Đối chiếu schema/migration hiện có với DB local và DB thử, xác định migration đã áp hay chưa trước khi quyết định sửa hoặc thêm migration.

Đầu ra: bảng sai lệch và danh sách file/caller bị ảnh hưởng trong task; D1–D5 được trình với căn cứ.

### 2. Soạn nháp và chốt spec

1. Soạn bản nháp theo template của skill, trình trong hội thoại hoặc lưu bản nháp cùng plan; chỉ thay `specs/platform.md` sau khi nội dung mới đã chốt.
2. Mỗi route có mô tả, permission/vai trò mặc định, phạm vi, BR, DTO/request, response, bảng lỗi và điều kiện, transaction/lock/tác dụng phụ, ví dụ và test:
   - GET /api/v1/platform/stores.
   - POST /api/v1/platform/stores.
   - POST /api/v1/platform/stores/{id}/suspend.
   - POST /api/v1/platform/stores/{id}/reactivate.
   - GET /api/v1/users?role=OWNER.
   - POST /api/v1/users.
   - POST /api/v1/users/{id}/reset-password.
3. Ghi rõ nullable/trim/độ dài, UUID, query/body thừa, Origin/CSRF, ID thiếu hoặc sai vai trò; cách xử lý request lặp và mất response chứa mật khẩu tạm; đầu vào phân trang theo D1.
4. Rà mâu thuẫn với API/auth/DB/DESIGN; cập nhật tài liệu chung bị ảnh hưởng cùng quyết định. Chốt phiên bản spec trước triển khai phần phụ thuộc.

Đầu ra: spec hoàn chỉnh đã chốt, bảng permission từng route, hợp đồng dữ liệu và ma trận nghiệm thu kiểm thử được.

### 3. API/DB và kiểm soát phiên

1. Đọc rules clean-code/coding-style/naming/database/security/testing trước khi sửa tương ứng.
2. Viết hoặc điều chỉnh test theo hợp đồng chốt để tái hiện sai lệch; sửa migration/DTO/controller/service/guard trong phạm vi cần thiết.
3. Kiểm tra create store+OWNER atomic, cấp OWNER đúng store; không nhận role/tenant tùy ý; username chuẩn hóa và unique khi đồng thời.
4. Kiểm tra khóa/mở/reset: transaction, thứ tự lock nhất quán với login/refresh, không tạo phiên lọt qua lúc khóa, không phục hồi token cũ, không mất dữ liệu store khác.
5. Danh sách không chứa dữ liệu vận hành, hash hoặc mật khẩu; log action/actor/target/requestId/thời gian không chứa secret. Phân trang và lỗi đúng spec mới.

Files dự kiến: `POS_API/src/platform/*`, migration platform, `auth/auth.service.ts`, `auth/security/access.guard.ts`, test auth/foundation và app module khi thực sự cần.

### 4. Nối UI demo hiện có

1. Sửa `POS_UI/src/features/platform/PlatformAdminScreen.tsx` và `services/platformService.ts`, App/AppShell/types liên quan theo hợp đồng mới; dùng component hiện có.
2. Luồng danh sách, tạo/cấp/reset, khóa/mở, reload; loading/empty/error và chống gửi lặp từ thao tác UI. Thông báo tiếng Việt, tablet ngang.
3. Mật khẩu tạm chỉ ở trạng thái hiển thị một lần, không storage/URL/log; xử lý đóng modal theo D4. Phiên hết hạn refresh rồi retry có giới hạn; phiên thu hồi về login.
4. Bỏ mock ở đúng phần đã nối API; các màn chưa nối tiếp tục ghi rõ dữ liệu mẫu. Không tạo trang quản trị thay thế ngoài giao diện hiện có.

Đầu ra: luồng browser gọi API thật, đáp ứng D1/D4; test service/session có ý nghĩa cho nhánh logic thay đổi.

### 5. Kiểm thử và thu chứng cứ trên phiên bản cuối

Trước khi chạy, lập matrix từng vế tiêu chí → case ID → expected → artifact. Tạo run mới chỉ khi có thực thi thật; ghi SHA nền, dirty/diff hoặc phiên bản được kiểm tra, môi trường, giờ bắt đầu/kết thúc, lệnh, exit code, số test và output runner. Không dùng artifact UI cũ cho UI mới.

| Nhóm | Tình huống cần kiểm tra | Dấu vết |
| --- | --- | --- |
| Tạo/cấp | thành công, rollback lỗi giữa transaction, trùng hoa thường/request lặp/đồng thời, ID sai/thiếu, hai store | API request/response, runner, DB trước/sau |
| Quyền | thiếu auth, thiếu permission, OWNER/MANAGER/CASHIER bị cấm platform, quyền hiện hành thay đổi, admin không có quyền vận hành | test guard/HTTP; nêu rõ giới hạn API chưa có theo D5 |
| Khóa/mở | reason thiếu, trạng thái lặp, hai phiên sống, login/refresh lúc khóa, mở lại yêu cầu login, store khác không bị ảnh hưởng | browser trước/sau, network, DB session trước/sau |
| Reset | đúng OWNER, non-OWNER/ID thiếu, store khóa, password cũ vô hiệu, must_change=true, thu hồi nhiều phiên | HTTP/DB, browser và log action |
| UI/secret | modal, đóng/reload, lỗi tiếng Việt, tablet, refresh/revoked, không secret trong storage/URL/list/log | snapshot/ảnh viewport, network/console gốc đã che, cookie metadata |
| Hồi quy | API/UI build/test và PB-01/PB-02 bị ảnh hưởng | stdout/stderr/report runner |

Lệnh đã có: `npm run build --prefix POS_API`, `npm run build --prefix POS_UI`, `npm test --prefix POS_UI`; dựng API/UI bằng `docker compose --env-file POS_INFRA/.env.local -f POS_INFRA/compose.local.yml up -d --build api ui`; API integration qua `docker compose --env-file POS_INFRA/.env.local -f POS_INFRA/compose.local.yml exec -T api npm test`. Kiểm tra cấu hình trước khi chạy, dùng DB thử cho case thay đổi dữ liệu, không xóa volume local.

3. Thiếu bằng chứng thì chạy lại đúng case, QA rà lại phần bổ sung; không tick dựa trên mô tả.
4. Trình Product Owner bảng đạt/chưa đạt theo phiên bản cuối. Cập nhật sprint, spec, plan và task thống nhất với quyết định.
